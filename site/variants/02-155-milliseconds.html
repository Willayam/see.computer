155 ms, on the CPU, with the network cable out

The speech model is NVIDIA Parakeet TDT 0.6b v3, quantised to INT8 and run through ONNX on the CPU. No upload, no round trip. On an M3 Max a six-second Swedish sentence comes back in about 155 ms after key up.

The number is small because the work starts early. The engine is warmed the moment the trigger goes down, while you are still talking. By the time you release, the only thing left is the decode.

A take is a folder an agent can read

Hold the trigger with Shift and talk through what is on screen. On release, see.computer writes the screen recording, a transcript, and a JPEG frame for each moment you said something. An agent that can read files opens the exact frames where each thing was said, without decoding the video. A human, or a web chatbox, still gets the words.

What gets fixed before the paste

Raw transcripts are honest and unreadable. see.computer does three edits between the model and your cursor, each with a rule you can predict.

Hesitation goes 01

"um", "uh" and "hm" are dropped, along with the comma or full stop stuck to them, and the next word takes over the capital. So Um, the build is failing pastes as "The build is failing." A dictation that was only a hum pastes nothing at all.

"like" and "actually" stay, because they are usually real words. "er" stays because it is Swedish for "your". A filler list that ate Swedish would be worse than no list.

Ten and above are digits. Zero to nine stay as words unless they carry a percent sign or a decimal point. English and Swedish.

Your words, inside the decoder 03

Put the words the model misses in ~/Documents/see.computer/vocabulary.md, one per line. They are not swapped in afterwards. They are pushed into the decoder while it is still choosing, so the spelling you wrote is the one that wins a close call. The file is re-read on change, no restart.

A term only gets its bonus when the model was already considering it. That is what keeps a long list safe. A bonus can win a close call. It cannot overturn a confident one.

The pill tells you what the mic is doing

A small chip sits at the bottom of the screen while the trigger is down. Cyan bars while listening, scaled to the loudest thing heard lately, so a quiet room still moves. Red while recording. A lit ring when a take is locked, because a live mic should never look idle.

History is one markdown file per day in ~/Documents/see.computer/. Nothing is auto-pruned. They are plain files, so read them or delete them. Turn the whole thing off with "Save Dictation History" in Settings.

One caveat worth saying out loud. Audio never leaves the machine, but transcript files are ordinary files in Documents. If iCloud Desktop & Documents sync is on, they will sync like anything else in that folder.

What macOS will ask for, and why

Each prompt maps to one mechanism. None of them are for telemetry, because there is none.

to press Cmd+V

Accessibility

The paste is a real Cmd+V sent to the front app. macOS gates synthetic keystrokes behind Accessibility.

to see a bare modifier go down

Input Monitoring

Holding Option on its own is not a shortcut the system will report. Reading that hold, and the release, needs Input Monitoring.

to hear you

Microphone

Audio is transcribed on the CPU. It is never uploaded.

only if you use the video hotkey

Screen Recording

Only the video hotkey needs it. If you only dictate, leave it unset.

How it stays fast

One controller thread owns the app state. Every thread names its scheduling class, and the hotkey path runs user-interactive, the highest class macOS offers.

The menu bar panel is native AppKit with NSGlassEffectView, not a web view pretending. There is no bundler and no Node toolchain. Build it yourself with cd src-tauri && cargo tauri build --debug --bundles app.
